# Provider assumptions

Every external contract aiecon depends on, with the page it was checked against, the date
of the check, the fixture that exercises it, and its live-validation status. When a provider
changes a contract, keep the data, mark the affected calls `unsupported`/`unknown`, and fix
the adapter and its fixture. Never adjust amounts to hide a difference.

day; quotes below are verbatim from the fetched pages. Items marked `UNVERIFIED` could not
be confirmed from an official page and are treated as unknown in code.

## Usage formats (`usage_format`)

The parser is chosen by `usage_format`, never by provider name (PLAN.md section 5.1). All
adapters produce the same mutually exclusive classes:
`input_total = input_uncached + input_cache_read + input_cache_write`, plus `output`.

### `openai_chat_completions` (S3)

| Field | Meaning (verbatim) | aiecon mapping |
| --- | --- | --- |
| `prompt_tokens` | "Number of tokens in the prompt." | `input_total` |
| `prompt_tokens_details.cached_tokens` | "Cached tokens present in the prompt." | `input_cache_read` |
| `prompt_tokens_details.cache_write_tokens` | "The unadjusted number of prompt tokens written to cache." | `input_cache_write` |
| `completion_tokens` | "Number of tokens in the generated completion." | `output` |
| `completion_tokens_details.reasoning_tokens` | "Tokens generated by the model for reasoning." | not added: "billed as output tokens" and "counted in the total completion tokens" |

`input_uncached = prompt_tokens - cached_tokens - cache_write_tokens`. If `cached_tokens` is
absent the call is `partial` (the split is unknown). If `cache_write_tokens` is absent the
adapter records `input_cache_write = 0` with the note `cache_write_field_absent`; the
estimator treats that as "writes folded into uncached", which is exact for models with no
cache-write charge and a lower bound (flagged, `cost_complete=false`) for models that bill
writes. Fixtures: `tests/fixtures/usage/openai_chat_*.json` (T2.2).

### `openai_responses` (S3)

Same rules with `input_tokens`, `input_tokens_details.cached_tokens` ("The number of tokens
that were retrieved from the cache."), `input_tokens_details.cache_write_tokens` ("The number
of input tokens that were written to the cache."; required in the spec), `output_tokens`,
`output_tokens_details.reasoning_tokens`. Streaming: final usage comes from
`response.completed.response.usage`.

### `anthropic_messages` (S4)

| Field | Meaning (verbatim) | aiecon mapping |
| --- | --- | --- |
| `input_tokens` | "Number of input tokens which were not read from or used to create a cache (that is, tokens after the last cache breakpoint)." | `input_uncached` |
| `cache_read_input_tokens` | "Number of tokens retrieved from the cache for this request." | `input_cache_read` |
| `cache_creation_input_tokens` | "Number of tokens written to the cache when creating a new entry." | `input_cache_write` (consistency check only when tiers exist) |
| `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` | breakdown by TTL | `cache_write_breakdown`; the priced quantities |
| `output_tokens` | "output_tokens remains the inclusive, authoritative total used for billing." | `output` |

"Total input tokens in a request is the summation of `input_tokens`,
`cache_creation_input_tokens`, and `cache_read_input_tokens`." A write total without a
breakdown is kept but marked `cache_write_tier_unknown` and left unpriced: the TTL tier is
never guessed.

Streaming: "The token counts shown in the `usage` field of the `message_delta` event are
*cumulative*." The final `message_delta.usage` is authoritative for output (and for input
fields when present); cache fields arrive in `message_start`. aiecon takes the last delta and
falls back to `message_start` for fields the delta reports as `null`. Cumulative values are
never summed across deltas (V04).

### `litellm_standard` (S5)

LiteLLM's transformed `Usage` object is OpenAI-shaped. For Anthropic responses it already
folds cache tokens into `prompt_tokens` and exposes `cache_creation_input_tokens` and
`cache_read_input_tokens` next to it; the 5m/1h breakdown sits under
`prompt_tokens_details.cache_creation_token_details` (observed live with 1.102.1 on
2026-09-28; the top-level `cache_creation_token_details` documented earlier is still
accepted). The adapter treats `prompt_tokens` as the total and subtracts the cache classes;
applying the native Anthropic sum again would double count. Every field outside the
allowlist is counted as `schema_drift` by name only.

Observed live (2026-09-28, gpt-5-nano and claude-haiku-4-5-20251001 through the proxy):

- OpenAI non-streaming responses report the dated model id (`gpt-5-nano-2025-08-07`),
  streamed ones the bare alias; Anthropic streamed responses report the LiteLLM model
  group name (`anthropic-live`) instead of a model id, which the collector now discards so
  `model_requested` is used.
- `prompt_tokens_details.cached_tokens` is populated for OpenAI automatic caching
  (`prompt_cache_key`), as expected: 27,264 of 27,331 prompt tokens on the repeat calls.
- LiteLLM adds `cost`, `service_tier` and `inference_geo` to the usage object on some
  paths. `service_tier` is captured as a code (`standard` observed); `inference_geo` is
  kept only when it is a known region code (`global`, `us`): Anthropic answers
  `not_available` for default routing, which is recorded as no region so the global price
  applies (a literal `not_available` region made every call unpriceable on 2026-09-28).
  `cost` is kept as `upstream_cost_estimate_usd` only.
- gpt-5-nano spent the whole 120-token output budget on `reasoning_tokens` when no
  `reasoning_effort` was given; the workload now sends `minimal`.

Contract for absent cache counters in this format: LiteLLM only populates
`prompt_tokens_details.cached_tokens` / `cache_read_input_tokens` and the cache-creation
counters when the provider reported cache usage; a `null` or absent counter therefore means
"no cache usage reported" and the adapter records `0` with the notes
`cache_read_absent_treated_as_zero` / `cache_write_absent_treated_as_zero` (observed with
LiteLLM 1.102.1 mock responses, whose `prompt_tokens_details` is `null`). The native
`openai_*` formats keep the stricter rule (absent split = `partial`).

## Cache billing contracts

| Model | Min cacheable prefix | Write charge | Read charge | Source |
| --- | --- | --- | --- | --- |
| OpenAI GPT-5.6 and later | "1,024 visible input tokens" | "1.25x the uncached input-token rate" | "0.1x the uncached input-token rate" | S3 |
| OpenAI earlier models (incl. gpt-5-nano) | "Varies by request settings" | "No additional cache-write charge" | "Model-dependent cached-input rate" | S3 |
| Claude Haiku 4.5 | 4,096 tokens | 5m: 1.25x base, 1h: 2x base | 0.1x base | S4 |
| Claude Sonnet 5 | 1,024 tokens | 5m: 1.25x base, 1h: 2x base | 0.1x base | S4 |

OpenAI: "Cache-write pricing is not an additive fee: input tokens use the uncached-input,
cached-input, or cache-write rate." Cache lifetime for GPT-5.6+ is `prompt_cache_options.ttl`
= `30m` (only value); earlier models use `prompt_cache_retention` (`in_memory` about 5-10
minutes of inactivity, `24h` extended). Cached tokens on earlier models are rounded down to
multiples of 128.

Anthropic: "By default, the cache has a 5-minute lifetime. The cache is refreshed for no
additional cost each time the cached content is used." Lifetime is measured from the start of
the request that writes or reads the entry. 1-hour TTL via `cache_control.ttl = "1h"`.
"These multipliers stack with other pricing modifiers such as the Batch API discount and
data residency" (US-only `inference_geo` is a 1.1x multiplier). aiecon v0.1 prices
`service_tier=standard`, `region=global` only; other tiers are unpriced, not approximated.

## Provider report APIs

### OpenAI (S1)

| Item | Costs | Usage (completions) |
| --- | --- | --- |
| Endpoint | `GET https://api.openai.com/v1/organization/costs` | `GET https://api.openai.com/v1/organization/usage/completions` |
| Auth | Admin API key, `Authorization: Bearer` ("Admin API keys cannot be used for non-administration endpoints.") | same |
| Time | `start_time` (Unix seconds, inclusive, required), `end_time` (exclusive) | same |
| Buckets | `bucket_width`: "Currently only `1d` is supported" | `1m`, `1h`, `1d` |
| Limit | 1-180 buckets, default 7 | 1d: max 31; 1h: max 168; 1m: max 1440 |
| Filters | `project_ids`, `api_key_ids`, `line_items` | `project_ids`, `user_ids`, `api_key_ids`, `models`, `batch` |
| `group_by` | `project_id`, `line_item`, `api_key_id` | `project_id`, `user_id`, `api_key_id`, `model`, `batch`, `service_tier` |
| Result object | `organization.costs.result`: `amount.value` (number), `amount.currency` ("Lowercase ISO-4217 currency e.g. \"usd\""), `line_item`, `project_id`, `api_key_id`, `quantity`, `quantity_unit` | `organization.usage.completions.result`: `input_tokens` ("including cached and cache-write tokens"), `input_cached_tokens`, `input_cache_write_tokens`, `input_uncached_tokens` ("excluding cache-write tokens"), `output_tokens`, `num_model_requests`, plus audio/image splits and grouping fields |
| Pagination | `has_more`, `next_page` cursor -> `page` | same |
| Latency | `UNVERIFIED` (help-center article not reachable) | `UNVERIFIED` |

Mapping: cost amounts are already in currency units (`amount_unit=usd`), so
`amount_usd = amount.value` when `currency == "usd"`; any other currency is kept but excluded
from USD totals. **There is no model grouping for costs**; `line_item` values look like
`"gpt-6-astra, input_tokens"` and are kept as the `line_item` dimension. Usage grain is what
was requested (`1d/model,project_id` by default in `billing sync`). `project_id: null` means
not grouped; aiecon writes the sentinel `not_grouped` for dimensions that were not requested.

### Anthropic (S2)

| Item | Cost report | Usage report (messages) |
| --- | --- | --- |
| Endpoint | `GET https://api.anthropic.com/v1/organizations/cost_report` | `GET https://api.anthropic.com/v1/organizations/usage_report/messages` |
| Auth | "Admin API credentials required." Admin API key (`sk-ant-admin01-...`) in `x-api-key`; `anthropic-version: 2023-06-01`. "The Admin API is unavailable for individual accounts." | same |
| Time | `starting_at` (RFC 3339, required; buckets snapped to UTC), `ending_at` | same |
| Buckets | "Daily granularity only (`1d`)" | `1d`, `1h`, `1m` |
| Limit | 1-31 | 1d: 31; 1h: 168; 1m: 1440 |
| `group_by` | `workspace_id`, `description` | `account_id`, `api_key_id`, `context_window`, `inference_geo`, `model`, `service_account_id`, `service_tier`, `speed`, `workspace_id` |
| Result fields | `amount` (string), `currency` ("Currently always `\"USD\"`"), `workspace_id`, `description`, `cost_type` (`tokens`, `web_search`, `code_execution`, `session_usage`), `context_window`, `model`, `service_tier`, `token_type` (`uncached_input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation.ephemeral_5m_input_tokens`, `cache_creation.ephemeral_1h_input_tokens`), `inference_geo` | `uncached_input_tokens`, `cache_creation.ephemeral_5m_input_tokens`, `cache_creation.ephemeral_1h_input_tokens`, `cache_read_input_tokens`, `output_tokens`, `server_tool_use.web_search_requests`, grouping fields |
| Pagination | `has_more`, `next_page` -> `page` | same |
| Latency | "Usage and cost data typically appears within 5 minutes of API request completion, though delays may occasionally be longer." Polling: "once per minute for sustained use." | same |

**Amount unit (verbatim):** "Cost amount in lowest currency units (e.g. cents) as a decimal
string. For example, `\"123.45\"` in `\"USD\"` represents `$1.23`." aiecon converts with
`Decimal`: `"123.45"` cents -> `"1.2345"` USD (`amount_unit=cents`). Unknown currency or unit
is rejected from USD totals (V13).

**Default workspace (verbatim):** "Usage and costs attributed to the default workspace have a
`null` value for `workspace_id`." aiecon keeps `workspace_id: null` distinct from
`not_grouped` and from an absent field.

Exclusions: "Priority Tier costs use a different billing model and are not included in the
cost endpoint." Code execution appears in cost (description `Code Execution Usage`) but not
in usage. Model IDs in reports may be dated snapshots (`claude-haiku-4-5-20251001`) even
when requests used the alias (`claude-haiku-4-5`); the catalog maps both to one price row.

### File import (PLAN.md section 7.4)

## LiteLLM hooks (S5)

Request-level hooks fire once per logical request: "async_log_success_event and
async_log_failure_event are documented as request-level hooks: each is meant to fire once
per logical client request." Per-attempt hooks: "each one is guaranteed to fire once for
every real deployment call, including the original attempt, every retry, and every fallback
step, with no dedup logic involved."

| Hook | Signature (verbatim) | aiecon use |
| --- | --- | --- |
| `async_pre_call_deployment_hook` | `(kwargs, call_type)` - "runs before each deployment call, can modify the request" | allocate `call_id`, write `call_started` |
| `async_post_call_success_deployment_hook` | `(request_data, response, call_type)` | write `call_finished` (success) with allowlisted usage |
| `async_post_call_failure_deployment_hook` | `(request_data, exception, call_type, fallback_depth=None)` - "fallback_depth ... None on the original attempt, 1 on the first fallback hop" | write `call_finished` (error) with `error_class` only |
| `async_log_success_event` / `async_log_failure_event` | `(kwargs, response_obj, start_time, end_time)` | not used for attempts (request-level, deduplicated) |

"A fallback chain where the first two deployments fail and the third succeeds calls the
failure hook twice and the success hook once, in that order. request_data is that attempt's
own request kwargs, not shared state carried over from an earlier attempt." Proxy
registration: `litellm_settings: callbacks: custom_callbacks.proxy_handler_instance`.
`kwargs["standard_logging_object"]["metadata"]` is the documented place for request identity;
`response_cost` "Cost of the response in USD ($)" is kept only as
`upstream_cost_estimate_usd`, never as billing.

**Observed hook arguments (probe against LiteLLM 1.102.1 on 2026-09-27, both via
`Router` and via the proxy):** the pre-call deployment kwargs carry the bare deployment
`model` (for example `gpt-5-nano`), `max_tokens`, `stream`, `litellm_call_id`,
`litellm_trace_id`, `api_key`, `messages` and a `metadata` dict with `model_group`,
`deployment`, `deployment_model_name`, `model_info`, `attempted_retries` and
`attempted_fallbacks`; there is no `litellm_params` key at this stage. The failure hook
receives a read-only view of the same kwargs and an exception whose `llm_provider` names the
provider. aiecon therefore resolves the provider from the model id (explicit prefix, known
families, then LiteLLM's own `get_llm_provider`), reads `model_group` from `metadata`,
keeps `litellm_trace_id` / `litellm_call_id` only as opaque correlation ids, allocates its
own per-attempt `call_id` in the pre-call hook and carries it in a copied `metadata`. It
never reads `api_key` or `messages`. Verified end to end with placeholder keys: two attempts
for one node run produced two calls with explicit lineage, `error_class=auth`, and no key or
prompt text in the JSONL.

## Unverified items

- OpenAI cost/usage report data latency and finalization behaviour.
- OpenAI "short context" vs "long context" threshold for GPT-6 models (labels say `<272K` for
  gpt-5.5/5.4 only); the live catalog therefore omits gpt-6 models.
- USD as the OpenAI pricing page currency is implied by `$` figures, not stated in a sentence.
- The values of the nested Anthropic cache-creation breakdown were not retained on the
  first live call (the allowlist of that build dropped them); the fixture fills them in as
  all-5m, which the request asked for. The next Anthropic run records them verbatim.
